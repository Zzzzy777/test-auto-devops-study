# 软件测试全流程笔记

## 一、软件与软件测试基础
**软件**：控制计算机硬件工作的工具。

**软件产生完整过程**
需求产生 → 输出需求文档 → 设计效果图 → 产品开发 → 产品测试 → 部署上线

**软件测试定义**
使用技术手段验证软件是否满足使用需求；不只是找Bug，还要评估产品质量风险。

**软件测试目的**
减少软件缺陷(bug)，保证软件质量。

实际工作测试目的：
1. 尽早发现缺陷，降低缺陷修复成本；需求阶段改问题成本最低，线上修复成本最高。
2. 评估当前版本质量，给上线决策提供依据。
3. 不仅仅找bug，还要确认功能符合用户真实使用场景。

### 测试主流技术
1. **功能测试**：主要验证程序的功能是否满足需求。
手工测试核心，黑盒测试最常用，不需要看懂代码。
2. **自动化测试**：使用代码或工具代替手工，对项目进行测试。
适合回归测试、重复执行的用例；不能完全替代手工测试。
3. **接口测试**：使用代码或工具对服务端提供的接口进行测试。
前后端分离项目重点；在UI页面未开发完成就可以开展，提前发现后端逻辑bug。
4. **性能测试**：模拟多人使用软件，查找服务性能瓶颈。
关注：响应时间、并发数、吞吐量、服务器CPU内存占用。

基础流程
①需求分析 ②设计测试用例 ③搭建测试环境 ④执行测试 ⑤异常场景测试 ⑥缺陷提交与跟踪 ⑦测试总结

实操说明
- 需求分析：读懂需求文档，主动找产品确认歧义点，需求有疑问不能自己猜。
- 搭建测试环境：和线上环境尽量保持一致；禁止直接在生产环境做测试。

## 二、软件测试分类
### 按测试阶段划分
1. **单元测试**：针对程序源代码进行测试
执行主体：开发人员；测试最小代码单元，函数、方法。
2. **集成测试**：接口测试，针对模块之间访问地址进行测试
重点：模块之间数据传递、调用逻辑；模块单独没问题，组合之后容易出bug。
3. **系统测试**：对整个系统进行测试，包括功能、非功能（兼容、文档等内容）
测试人员主要做的阶段；完整系统，包含功能、UI、兼容性、安全。
4. **验收测试**：主要分为内测、公测，使用不同人群来对项目做验证。
内测：公司内部人员使用；公测：真实外部用户。验收通过才允许上线。

### 按代码可见度划分
1. **黑盒测试**：不关注源代码，仅对程序输入输出进行测试（多用于系统测试）
只看输入输出，不管内部怎么实现；手工功能测试绝大多数是黑盒。
2. **灰盒测试**：针对程序部分代码进行测试（多用于集成测试）
看接口、数据库，不深入底层源码；接口测试属于灰盒。
3. **白盒测试**：针对程序源代码进行测试（多用于单元测试）
看代码逻辑、分支、循环，覆盖代码路径，一般开发执行。

其他常见测试分类
- 冒烟测试：新版本交付后，优先跑核心主流程，判断版本是否具备可测条件。核心流程跑不通直接打回开发，不用测细节用例。
- 回归测试：bug修复完成、版本迭代之后，重新执行相关用例，防止改一个bug引出新bug。
- 兼容性测试：不同浏览器、不同操作系统、不同分辨率。
- 安全测试：密码泄露、越权访问、SQL注入等。

## 三、软件质量模型
衡量一个优秀软件的维度
从下面8点进行衡量：**功能性、性能、兼容性、易用性、可靠性、安全、可维护性、可移植性**

1. **功能性**：功能是否满足需求，能不能干该干的事。
2. **性能**：响应速度、并发能力。
3. **兼容性**：不同设备、浏览器、系统是否正常使用。
4. **易用性**：用户好不好上手，操作是否简单。
5. **可靠性**：长时间运行稳定，不容易崩溃。
6. **安全性**：数据保护，防止越权、泄露。
7. **可维护性**：后期代码方便迭代修改。
8. **可移植性**：软件可以在不同环境部署运行。

## 四、软件测试完整工作流程
需求评审 → 测试计划编写 → 用例设计 → 用例执行 → 缺陷管理 → 测试报告

每个环节工作内容
1. **需求评审**：产品、开发、测试一起评审需求文档，测试提出需求模糊、逻辑冲突点。
2. **测试计划**：测试范围、时间、人员、环境、风险。
3. **用例设计**：根据需求编写测试用例。
4. **用例执行**：版本提测，执行用例，不通过就提交bug。
5. **缺陷管理**：提交bug、跟踪bug、验证修复、关闭bug。
6. **测试报告**：统计用例执行率、bug情况，给出版本上线风险结论。

## 五、测试用例基础
1. 用例：用户使用的案例
2. 测试用例：是为测试项目而设计的执行文档
3. 测试用例的作用：防止漏测，实施测试标准

### 用例编写字段
- **用例编号**：项目_模块_编号
- **用例标题**：预期结果（测试点）
- **模块/项目**：所属模块或者项目
- **优先级**：表示用例的重要程度或影响力 P0~P4（P0最高）
P0核心主流程，阻断，不通过版本不能上线；P1重要功能；P2次要；P3优化建议。
- **前置条件**：要执行此条用例，有哪些前置条件
- **测试步骤**：描述操作步骤
- **测试数据**：操作的数据，没有的话可以为空
- **预期结果**：期望达到的结果

用例执行不通过为缺陷，需进行缺陷管理。

实操要点
- 用例标题：动作+输入+预期结果，别人不看需求也看得懂。
- 测试步骤：一步一个操作，步骤不能跳，其他人可以直接照着复现。

## 六、缺陷Bug基础
### 1、缺陷定义
软件在使用过程中有任何问题都叫软件的缺陷，简称bug。

### 2、判定缺陷标准
①少功能 ②功能错误 ③多切功能 ④隐性功能错误 ⑤不易使用

补充：需求没有提到，但是严重影响用户体验，也可以提交缺陷。

### 3、缺陷产生的原因
1. 需求阶段：需求描述不理解，有歧义，错误等；
2. 设计阶段：设计文档存在错误或者有缺陷；
3. 编码阶段：代码出现错误；
4. 运行阶段：软硬件系统本身故障导致软件缺陷。

补充统计：大部分bug根源来自需求、设计，不完全是开发写代码错。

### 4、软件缺陷的核心内容
1. 缺陷的标题：描述缺陷的核心问题
2. 缺陷的预置条件：缺陷产生的前提
3. 缺陷的复现步骤：复现缺陷的过程
4. 缺陷的预期结果：希望得到的结果
5. 缺陷的实际结果：实际得到的结果
6. 缺陷的必要附件：图片、日志等信息（证据）

工作重点：复现步骤必须清晰，步骤要1、2、3，开发拿着你的步骤就能复现bug。

### 5、缺陷提交要素
1．缺陷报告编号
2．严重程度：阻断、严重、一般、次要、建议
严重程度：bug造成的破坏大小。阻断：直接用不了；严重：主要功能失效；一般：部分功能异常；次要：UI文案类问题；建议：优化类需求。
3．缺陷优先级：bug需要多快修复。
严重程度 ≠ 优先级。例如UI错别字严重程度低，但优先级可以高，上线前要改掉。
4．Bug类型：功能bug、UI、兼容性、安全、性能
5．缺陷状态：新建→指派→已修复→待验证→关闭 / 重新打开

常见bug状态流转：
新建(测试提交)→指派给开发→开发修复改为已修复→测试验证；修复成功关闭；没修好重新打开。

## 七、五大测试用例设计方法
1. **等价类划分法**：针对需要有大量数据输入，但是没法穷举的地方。
2. **边界值分析法**：bug高发，重点测边界临界点。
3. **判定表法**：多个条件有依赖关系，条件组合测试。
4. **场景法（流程图法）**：按照实际业务场景设计用例。
5. **错误推测法**：所有用例覆盖完成，bug修复完成，离上线还有时间，以经验覆盖主要业务或者主要功能。

实操：项目中不会单独只用某一种方法，一般组合使用。
