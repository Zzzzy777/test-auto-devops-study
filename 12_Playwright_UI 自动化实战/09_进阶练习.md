# 09 进阶练习

基础用例稳定后，可以按风险和收益逐步增加以下能力。不要为了“用上所有 API”而增加无业务价值的复杂度。

## 1. Trace Viewer

Trace 能记录页面快照、操作、网络和控制台信息，适合分析 CI 中的偶发失败。

命令示例：

```powershell
pytest test_ui/test_ruoyi_user_add.py --tracing=retain-on-failure
```

如果当前版本参数不同，可查看：

```powershell
pytest --help | Select-String tracing
```

排查思路：

```text
失败步骤
  → 查看操作前页面快照
  → 查看 locator 实际匹配
  → 查看网络请求/响应
  → 查看控制台错误
```

## 2. 保存登录状态

当测试用例很多时，可以复用登录状态减少重复登录，但要注意状态过期和用例隔离。

```python
context = browser.new_context()
page = context.new_page()
page.goto("http://localhost:82/login")
# 完成登录后保存
context.storage_state(path=".auth/admin.json")
```

后续使用：

```python
context = browser.new_context(storage_state=".auth/admin.json")
```

不要把包含真实 token 的 `.auth` 文件提交到 Git，应加入 `.gitignore`。

## 3. 参数化测试

相同业务、不同数据可以使用 pytest 参数化：

```python
import pytest

@pytest.mark.parametrize(
    "username,password,expected",
    [
        ("admin", "admin123", True),
        ("admin", "wrong", False),
    ],
)
def test_login_variants(page, username, password, expected):
    # 执行登录并根据 expected 断言结果
    pass
```

参数化适合边界数据和等价类，不适合把十几条完全不同业务流程硬塞进一个用例。

## 4. 标记和分组

项目已在 `pytest.ini` 中配置 UI/API 标记，可按模块执行：

```python
import pytest

@pytest.mark.ui
def test_user_search(user_page):
    pass
```

运行：

```powershell
pytest -m ui
pytest -m api
pytest -m "ui or api"
```

分组标准应该服务于执行策略，例如冒烟、回归、UI、API、性能，而不是创建大量没有区别的标签。

## 5. 并行执行

pytest-xdist 可以并行执行独立用例：

```powershell
python -m pip install pytest-xdist
pytest test_ui test_api -n 2
```

并行前必须确认：

- 测试数据是唯一的
- 用例之间没有执行顺序依赖
- 测试账号允许并发登录
- 清理逻辑不会删除其他用例数据
- 浏览器和服务端资源足够

项目使用 UUID 数据和 API 清理，为并行执行提供了基础。

## 6. 网络监听与拦截

### 监听响应

```python
with page.expect_response(
    lambda response: "/system/user/list" in response.url
) as response_info:
    page.get_by_role("button", name="搜索").click()

response = response_info.value
assert response.ok
```

### 监听请求

```python
with page.expect_request(
    lambda request: request.method == "POST" and "/system/user" in request.url
):
    user_page.submit_user()
```

网络断言可以帮助判断“页面没有数据”到底是前端渲染问题还是后端接口失败。

## 7. APIRequestContext 与 Requests 的选择

Playwright 的 `APIRequestContext` 适合和浏览器上下文共享配置或 token；本项目使用 Requests，是因为 API 客户端需要独立承担数据清理和接口封装。

选择原则：

| 场景 | 推荐 |
|---|---|
| 与浏览器上下文共享认证 | Playwright APIRequestContext |
| 独立接口自动化项目 | Requests |
| 数据库核对 | PyMySQL |
| 性能并发 | JMeter/Locust |

## 8. 截图、视频和 trace 的取舍

| 产物 | 优点 | 代价 |
|---|---|---|
| 失败截图 | 文件小、定位直观 | 信息有限 |
| 视频 | 能看到完整操作过程 | 占空间较大 |
| Trace | 包含快照、网络、控制台 | 需要学习查看方式 |
| 全量日志 | 适合追踪数据和流程 | 文本较多 |

CI 通常保留失败截图和 Allure；偶发问题再开启 trace 或视频，不建议每次永久保存所有大文件。

## 9. 质量门禁

可以在 Jenkins 中逐步增加：

- 用例失败即构建失败
- JUnit 失败数量趋势
- API 错误率门槛
- 性能 P95 阈值
- 代码格式和静态检查
- 测试数据残留检查

门禁必须来自业务要求或团队约定，不要随意设置一个没有依据的数字。

## 10. 练习路线

### 练习 A：参数化登录

完成成功登录、错误密码、空用户名三种数据。

### 练习 B：网络断言

新增用户时监听 `POST /system/user`，确认请求成功后再做页面断言。

### 练习 C：并行安全

同时启动两条新增用户用例，验证用户名不冲突且都能清理。

### 练习 D：偶发失败分析

开启 trace，故意缩短超时时间，分析页面是在等待哪个元素。

### 练习 E：质量门禁

让 Jenkins 在 `pytest` 非 0 退出码时失败，并归档失败截图和 JUnit。
