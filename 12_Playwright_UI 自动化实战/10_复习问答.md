# 10 复习问答

本章用于检查是否真正理解项目设计。回答时先说结论，再结合代码位置和实际报错说明。

## 1. 为什么选择 Playwright

建议回答结构：

1. 能操作真实浏览器，验证用户可见的业务流程。
2. 自带自动等待和 Locator，减少传统 Selenium 中大量手工等待。
3. 支持截图、trace、网络监听、多浏览器和 headless 执行。
4. 能和 pytest、Allure、Jenkins 组合成完整测试工程。

## 2. Locator 和 ElementHandle 有什么区别

Locator 是延迟解析的定位器，执行操作时会重新查找并自动等待；ElementHandle 是某一时刻拿到的元素句柄，页面变化后可能失效。业务用例优先使用 Locator。

## 3. 为什么 `get_by_text("确定")` 可能失败

因为页面可能有多个弹窗、隐藏元素或多个相同按钮。应该先限定当前可见弹窗，再定位弹窗内的按钮，例如：

```python
page.locator(".el-dialog:visible").filter(
    has_text="添加用户"
).get_by_role("button", name="确定").click()
```

## 4. 自动等待和 `sleep` 的区别

自动等待针对元素可见、可用、稳定等条件，在条件满足后立即执行；`sleep` 只是固定暂停，无法适配不同机器和网络速度。优先等待业务状态，不能把 sleep 当成稳定性方案。

## 5. 为什么要使用 `expect`

`expect` 会在超时时间内自动重试断言，适合异步渲染的 URL、文本、表格和弹窗。断言应该验证业务结果，不只是验证某个按钮被点击。

## 6. 为什么使用 Page Object

Page Object 把定位器和页面操作集中起来。页面 DOM 改动时，通常只修改页面对象，测试用例仍然保持业务语义，降低维护成本。

## 7. fixture 在项目中解决什么问题

`page` fixture 负责页面初始化和失败截图；`user_page` fixture 负责登录并进入用户管理页面。测试用例可以直接从业务动作开始，避免每条用例重复登录和导航。

## 8. 为什么测试数据要使用 UUID

固定用户名容易和已有数据冲突，也容易被其他执行者修改。UUID 能让每次测试数据唯一，支持重复执行和一定程度的并行执行。

## 9. 为什么清理逻辑放在 `finally`

无论测试通过、断言失败还是定位器超时，`finally` 都会执行。这样可以尽量清理测试数据，避免污染环境。

## 10. 为什么用 API 清理 UI 测试数据

UI 清理需要重新定位表格、点击删除、处理确认弹窗并等待刷新，步骤多且容易受页面变化影响。API 清理只需要根据用户名查询 userId 后调用删除接口，更快更稳定。UI 仍然负责验证真实新增流程。

## 11. HTTP 200 是否代表接口成功

不一定。HTTP 200 只说明网络请求完成，RuoYi 还需要检查 JSON 中的业务 `code`，并对返回数据做进一步断言。

## 12. Jenkins 为什么找不到 `test_ui`

因为仓库根目录和项目目录不是同一层。Jenkins checkout 到仓库根目录，测试代码在 `Ruoyi_full_auto_test/test_ui`，因此 Jenkinsfile 必须使用 `dir('Ruoyi_full_auto_test')` 或显式添加目录前缀。

## 13. 为什么 CI 使用 headless

CI 通常没有人工观察浏览器窗口的需求，headless 占用资源更少、执行更快。开发定位问题时使用 headed 和 slowmo，Jenkins 回归时使用 headless。

## 14. 失败时如何定位

按照以下顺序：

```text
测试名称和堆栈
  → 当前 URL
  → 失败截图
  → Locator 匹配数量
  → 页面元素状态
  → 网络请求和响应
  → 测试数据是否存在
  → 清理是否成功
```

## 15. JMeter 中为什么要动态提取 token

登录 token 通常每次登录都可能变化，不能把上一次的 token 写死。登录请求后使用 JSON 提取器获取 token，再通过 `Authorization: Bearer ${token}` 调用后续接口。

## 16. 如何区分产品问题和自动化脚本问题

先用浏览器或接口手工复现：

- 手工也失败：优先怀疑产品、环境或数据
- 手工成功、自动化失败：优先检查定位器、等待、数据和脚本逻辑
- 只有 CI 失败：检查 Agent 环境、工作目录、权限和浏览器安装

## 17. 解释一个真实排错案例

可以使用本项目的重复用户名问题：

```text
现象：重复用户名用例偶尔误判新增成功
原因：读取到了上一条用例残留的成功 Toast
分析：仅判断 Toast 不足以证明当前操作成功
修复：先判断弹窗状态，再判断当前错误提示，最后查询列表确认数据
验证：增加反向断言并执行全量回归
```
